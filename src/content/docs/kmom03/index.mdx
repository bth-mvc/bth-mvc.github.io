Den här veckan arbetar du med säkerhet som ett upplevt problem — inte som ett paket man installerar. Varje issue börjar med en attack mot din egna app. Du ser sårbarheten med egna ögon, förstår hur den utnyttjas och implementerar sedan skyddet i backenden. Tillsammans täcker veckans issues sex av OWASP Top Ten 2025-kategorierna: A01:2025, A02:2025, A04:2025, A05:2025, A07:2025 och A09:2025.

## Issues

Arbeta igenom issues i ordning. De flesta issues börjar med att du kör en attack mot din app, och avslutas med att du verifierar att attacken inte längre fungerar.

Du är välkommen att skriva egna kommentarer i varje issue medan du arbetar — noteringar, frågor eller korta reflektioner om vad du lärde dig. Det hjälper dig att minnas och ger läraren inblick i din process. Stäng ett issue när du anser att det är klart.

| Issue | Namn | Attack som demonstreras | Fix du implementerar |
|---|---|---|---|
| 03‑10 | `xss` | Ett namn med en `<img onerror>`-tagg körs som script varje gång namnet visas (lagrad XSS) | Sanera namnet med `sanitize-html` innan det sparas |
| 03‑20 | `samesite-cors` | En sida på annan site (`evil.html`) skickar med din inloggade cookie; en sida på annan origin (`evil-cors.html`) läser din data | `SameSite=strict` på JWT-cookien, explicit CORS origin-lista |
| 03‑40 | `helmet` | Svaren saknar säkerhetsheaders, och den lagrade XSS:en finns kvar i databasen | Helmet med genomgång av varje header, CSP anpassad till Svelte-frontenden som stoppar den lagrade XSS:en |
| 03‑50 | `rate-limiting` | Ett skript provar 15 lösenord i rad utan att stoppas | `express-rate-limit` på login och register |
| 03‑60 | `password-change` | Den som tar över en session kan byta lösenordet och låsa ute användaren | `PATCH /api/me/password` som kräver nuvarande lösenord — låser upp profilsidans formulär |
| 03‑70 | `crypto` | En lösenordshash hamnar i loggen | Redaction i loggern, mät bcrypts cost factor, varför `===` inte duger för lösenord |

Valfria issues — gör dem om du vill utforska vidare:

| Issue | Namn | Vad du gör |
|---|---|---|
| 03‑75 | `secure-logging` | Logga säkerhetshändelser (misslyckad och lyckad inloggning, registrering, lösenordsbyte) med strukturerade fält |
| 03‑80 | `brute-force` | Räkna misslyckade inloggningar per konto och lås kontot i 15 minuter efter fem |
| 03‑85 | `refresh-tokens` | Kortlivad access token och refresh token i databasen — roteras vid varje användning och tas bort vid utloggning |

## Redovisningstext

Skriv din redovisningstext i `report/kmom03.md` i ditt repo. Det är din egen reflektion över veckan, inte ett förhör. Bläddra gärna tillbaka genom veckans issues och föreläsningar för att påminna dig om vad du har gjort, och skriv sedan om det som fastnade: vad som var nytt, vad som var svårt och vad som klarnade längs vägen. Skriv på svenska eller engelska, ungefär en A4-sida. Lägg gärna till bilder, diagram och kodexempel om du vill — bilder kan du spara i `report/img/` och länka till därifrån.

Punkterna nedan lyfter fram veckans viktigaste delar och kan hjälpa dig att komma igång. Du behöver inte ta upp alla, och du behöver inte följa ordningen — en sammanhängande text är bättre än svar på frågor.

- **Attackerna** — Vilken attack gjorde störst intryck när du såg den fungera mot din egen app?
- **Skydden** — Vilka skydd har du lagt till (till exempel Helmet, CORS, SameSite-cookies, rate limiting), och vad skyddar de mot?
- **Lösenord** — Vad har du lärt dig om att hantera lösenord och lösenordsbyte på ett säkert sätt?
- **Ditt sätt att tänka** — Har din syn på säkerhet förändrats? Vad tänker du på nu när du skriver kod?
- Vad är din viktigaste insikt (TIL — Today I Learned) från veckan?

## Inlämning

1. Stäng alla obligatoriska issues, och de valfria som du har gjort klart.
2. Skriv klart din redovisningstext i `report/kmom03.md` och ta bort platshållartexten.
3. Verifiera att koden är ren innan du taggar:

```bash
npm run check
```

Alla kontroller ska passera — typecheck, lint, format och tester. Åtgärda eventuella fel innan du går vidare. Samma kontroller körs i CI, så här fångar du felen först.

4. Kör en självkoll som kontrollerar att redovisningstexten är klar och att alla obligatoriska issues är stängda:

```bash
npm run check-submission -- kmom03
```

5. Committa, tagga och pusha:

```bash
git add report/kmom03.md
git commit -m "Add kmom03 report"
git tag v3.0.0
git push origin main --tags
```

Kontrollera på GitHub att taggen syns under **Tags**.

Taggen startar ett CI-flöde på GitHub, under fliken **Actions**. Det kör samma kontroller som du körde lokalt, och bygger och startar dessutom appen och kör Bruno-testerna mot den. Vänta tills det är klart och kontrollera att det blir grönt. Blir det rött: öppna körningen, läs felet, åtgärda det och lämna in igen med en ny tagg (se nedan).

Behöver du uppdatera din inlämning efteråt? Committa ändringen och skapa en ny tagg med ökad patch-version, t.ex. `v3.0.1`, och pusha den. Flytta aldrig en tagg som redan är pushad.

6. Öppna en pull request från `main` till `bth/submit/kmom03` i ditt repo. CI körs även på pull requesten — kontrollera att den blir grön där också.

Läraren läser din redovisningstext via `report/kmom03.md` i PR:en.

### Fokus

Säkerhet som ett upplevt problem, inte ett paket man installerar. Varje issue börjar med en attack mot studentens egna app — studenten ser sårbarheten med egna ögon, förstår hur den utnyttjas, och implementerar sedan fixarna i backenden.

Attackerna körs mot studentens egen app, utan något "attack-läge" i UI:t. Svelte-frontenden har ett medvetet hål: headern renderar namnet med `{@html}` (03-10). Attacksidorna `public/evil.html` och `public/evil-cors.html` serveras med `npx http-server public/ -p 8080` och öppnas via `127.0.0.1:8080` (annan site) respektive `localhost:8080` (samma site, annan origin) i 03-20. Övriga attacker är curl-loopar, DevTools och serverloggen.

Studenterna kan sedan node-kursen: JWT i httpOnly-cookies, bcrypt, auth-middleware. Auth-koden finns färdigskriven i kursens template — den är inte ett lärandemål utan förutsättningen för att attackerna i det här momentet ska vara meningsfulla.

1. **Attacken** — studenten kör attacken mot sin app och ser vad som händer
2. **Förklaringen** — vad är sårbarheten, hur fungerar attacken, vad är risken i verkligheten
3. **Fixarna** — studenten implementerar skyddet i backenden
4. **Verifiering** — studenten kör demonstrationen igen och bekräftar att attacken inte längre fungerar

Klientens API-dokumentation räknar `POST /api/auth/register`, `login`, `logout` och `PATCH /api/me/password` till kmom03-gruppen **Säkerhet**. ### GET /api/me — profilvyn

Överväg att lägga till `GET /api/me` som ett issue i kmom03, kopplat till `password-change` (03-60). Motivering:

- `/api/me` är en naturlig resurs: GET hämtar profil, PATCH byter lösenord — samma resurs, två metoder
- Profilvyn kan visa namn + email direkt från databasen (inte sessionStorage-cachen) och därefter lösenordsformuläret
- Istället för att låsa upp profilvyn med `PATCH /api/me/password` låser den upp med `GET /api/me` — studenten måste implementera båda för att profilen ska vara komplett
- Gör det klickbart att klicka på inloggad användares email i headern → navigerar till `/profile`

Om det läggs till bör issue-numret vara 03-55 (mellan 03-50 rate-limiting och 03-60 password-change).

### Pedagogisk notering

Attack-first-upplägget kräver att kursteamet bygger demonstrationerna in i Svelte-frontenden. Det är ett icke-trivialt arbete men avgörande för att momentet ska fungera — en textuell beskrivning av en attack är inte alls lika effektiv som att se den köras.

**XSS** är den vanligaste sårbarheten på webben. Att se ett injicerat script köras i sin egna app är en stark upplevelse som är svår att glömma.

**CSRF** är extra relevant för den här kursen eftersom auth bygger på httpOnly-cookies — exakt den angreppsytan som CSRF exploaterar. `SameSite=strict` är en enradsfix men studenten förstår varför den behövs.

**CORS** hanteras ofta som "lägg till cors-paketet och sätt wildcard". Attacken visar att det läcker data.

Refresh tokens (valfritt, 03-85) ökar komplexiteten i auth-flödet märkbart och är veckans största issue. Det står i issuen.
