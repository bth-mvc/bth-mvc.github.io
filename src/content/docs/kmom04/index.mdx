### Fokus

Kärninsikten: integrationstester verifierar att systemet fungerar ihop; enhetstester av services verifierar affärslogiken isolerat. Mocka aldrig mer än du måste.

### Teststrategi per lager

```
Repository-lagret:
  Testas indirekt via integrationstester (mongodb-memory-server)
  Undvik att mocka Mongoose — det ger falsk trygghet

Service-lagret:
  Enhetstester med mockade repositories
  Testa affärslogiken isolerat, inga HTTP-anrop

Controller-lagret:
  Integrationstester med Supertest
  Testa hela kedjan: HTTP-anrop → svar
  Kräver auth-token i testerna (skapa testanvändare i beforeAll)
```

### Varför `mongodb-memory-server` och inte mocks

I node-kursen rekommenderades det att inte mocka databasen — den lärdomen bärs med hit. `mongodb-memory-server` startar en riktig MongoDB-instans i minnet för testerna. Det innebär att integrationstesterna testar hela stacken utom nätverket.

### Kodkvalitetskedjan

kmom04 är steget där den röda tråden från kmom01 formaliseras till en automatiserad kedja:

```
Editor        SonarLint              → direkt feedback medan man skriver
On-demand     npm run sonar          → manuell lokal scan mot SonarQube
Pre-push      sonar-scanner hook     → automatisk gate innan push
CI            ESLint + coverage      → gate i GitHub Actions
```

### Pre-push hook med sonar-scanner

`husky` hanterar git hooks i repot — det committas och fungerar på alla plattformar.

```bash
# .husky/pre-push
npm run typecheck
npm run lint
npm run sonar:ci
```

```bash
# package.json
"sonar:ci": "sonar-scanner -Dsonar.qualitygate.wait=true"
```

`sonar.qualitygate.wait=true` gör att `sonar-scanner` väntar på SonarQubes svar och returnerar exit code 1 om quality gate inte passerar. Pushen blockeras.

**Varför inte pre-commit?** En pre-commit hook som blockerar på formateringsfel i kmom01 är frustrerande friktion innan studenten förstår varför. SonarLint i editorn tar den rollen för löpande feedback. Pre-push är rätt nivå — koden är färdig nog att pushas och ska passera quality gate.

**Varför inte SonarCloud i CI:** Kursen kör privata repos i en GitHub-organisation. SonarCloud är gratis enbart för publika repos — privata kräver betalkonto. ESLint med komplexitetsregler och coverage-trösklar är en seriös CI-gate i sig.

### Pedagogisk notering

70% täckning på service-lagret är ett rimligt minimikrav. Täckning på repository-lagret fångas av integrationstesterna. Täckning på controller-lagret är sekundärt — om services är väl testade och integrationstesterna täcker happy path är risken låg.

Varning: det är lätt att fastna i mocking-djungeln. Läraren bör aktivt avråda från att mocka Mongoose, MongoDB eller hela HTTP-anrop inuti enhetstester.

- Bruno CLI i CI: inkluderat som valfritt issue 04-55. Contract tests i `bruno/contract/` med sekventiellt flöde. CI:s e2e-jobb kör dem automatiskt.
