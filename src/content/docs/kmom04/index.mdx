Den här veckan testar du varje lager i lagerarkitekturen på rätt sätt och formaliserar kodkvalitet som en automatiserad kedja — från editorn till CI. Du kan redan Vitest + Supertest från node-kursen, men där testade du routes med logik direkt i dem. Nu har du tre distinkta lager och varje lager testas på sitt eget sätt.

## Redovisningstext

Skriv din redovisningstext i `report/kmom04.md` i ditt repo. Det är din egen reflektion över veckan, inte ett förhör. Bläddra gärna tillbaka genom veckans issues och föreläsningar för att påminna dig om vad du har gjort, och skriv sedan om det som fastnade: vad som var nytt, vad som var svårt och vad som klarnade längs vägen. Skriv på svenska eller engelska, ungefär en A4-sida. Lägg gärna till bilder, diagram och kodexempel om du vill — bilder kan du spara i `report/img/` och länka till därifrån.

Punkterna nedan lyfter fram veckans viktigaste delar och kan hjälpa dig att komma igång. Du behöver inte ta upp alla, och du behöver inte följa ordningen — en sammanhängande text är bättre än svar på frågor.

- **Tester** — Vilka sorters tester har du skrivit, och vad testar de? Vad var svårast att testa?
- **Testmiljön** — Hur fick du databasen och inloggningen att fungera i testerna?
- **Kvalitetskedjan** — Vad fångas i editorn, i pre-push-hooken och i CI? Vad tyckte du om lint-reglerna för komplexitet och längd?
- **Förtroende** — Litar du mer på din kod nu än innan veckan?
- Vad är din viktigaste insikt (TIL — Today I Learned) från veckan?

## Inlämning

1. (Valfritt) Kör `npm run test:coverage` och sedan `npm run sonar`, så att SonarQube får färsk coverage. Jämför med en tidigare scan, till exempel den från kmom02: under **Activity** i SonarQube finns alla scanningar och deras siffror. Notera förändringar i din redovisningstext.
2. Stäng alla obligatoriska issues, och de valfria som du har gjort klart.
3. Skriv klart din redovisningstext i `report/kmom04.md` och ta bort platshållartexten.
4. Verifiera att koden är ren innan du taggar:

```bash
npm run check
```

Alla kontroller ska passera — typecheck, lint, format och tester. Åtgärda eventuella fel innan du går vidare. Samma kontroller körs i CI, så här fångar du felen först.

5. Kör en självkoll som kontrollerar att redovisningstexten är klar och att alla obligatoriska issues är stängda:

```bash
npm run check-submission -- kmom04
```

Issue-kontrollen kräver att du är inloggad i GitHub CLI (`gh auth login`). Annars hoppas den över, och då behöver du själv kontrollera att dina issues är stängda.

6. Committa, tagga och pusha:

```bash
git add report/kmom04.md
git commit -m "Add kmom04 report"
git tag v4.0.0
git push origin main --tags
```

Kontrollera på GitHub att taggen syns under **Tags**.

Taggen startar ett CI-flöde på GitHub, under fliken **Actions**. Det kör samma kontroller som du körde lokalt, och bygger och startar dessutom appen och kör Bruno-testerna mot den. Vänta tills det är klart och kontrollera att det blir grönt. Blir det rött: öppna körningen, läs felet, åtgärda det och lämna in igen med en ny tagg (se nedan).

Behöver du uppdatera din inlämning efteråt? Committa ändringen och skapa en ny tagg med ökad patch-version, t.ex. `v4.0.1`, och pusha den. Flytta aldrig en tagg som redan är pushad.

<summary>Planeringsanteckningar för läraren</summary>

### Fokus

Kärninsikten: integrationstester verifierar att systemet fungerar ihop; enhetstester av services verifierar affärslogiken isolerat. Mocka aldrig mer än du måste.

### Teststrategi per lager

```
Repository-lagret:
  Testas indirekt via integrationstester (mongodb-memory-server)
  Undvik att mocka Mongoose — det ger falsk trygghet

Service-lagret:
  Enhetstester med mockade repositories
  Testa affärslogiken isolerat, inga HTTP-anrop

Controller-lagret:
  Integrationstester med Supertest
  Testa hela kedjan: HTTP-anrop → svar
  Kräver auth-token i testerna (skapa testanvändare i beforeAll)
```

### Varför `mongodb-memory-server` och inte mocks

I node-kursen rekommenderades det att inte mocka databasen — den lärdomen bärs med hit. `mongodb-memory-server` startar en riktig MongoDB-instans i minnet för testerna. Det innebär att integrationstesterna testar hela stacken utom nätverket.

### Kodkvalitetskedjan

kmom04 är steget där den röda tråden från kmom01 formaliseras till en automatiserad kedja:

```
Editor        ESLint + SonarQube for IDE → direkt feedback (förslag)
Pre-push      check + test:coverage      → automatisk gate innan push (coverage från 04-50)
CI            check + coverage + Bruno   → gate i GitHub Actions (Bruno-jobbet e2e)
(valfritt)    npm run sonar / sonar:ci   → lokal SonarQube, on-demand eller i pre-push (04-60)
```

### Pre-push hook: coverage (04-50) och sonar-scanner (valfri 04-60)

`husky` hanterar git hooks i repot — det committas och fungerar på alla plattformar. Hooken kör `npm run check` från start. I 04-50 lägger studenten till `npm run test:coverage`, så att hooken kontrollerar samma sak som CI (tröskeln från 04-30); testerna körs då två gånger (några sekunder), vilket vi accepterar för att hålla hooken enkel. ESLint-reglerna från 04-40 är `warn` och stoppar inte pushen, medvetet. I den valfria 04-60 läggs scannern till; den behöver färsk `coverage/lcov.info`, som raden före skriver.

```bash
# .husky/pre-push
npm run check
npm run test:coverage   # färsk coverage/lcov.info till SonarQube
npm run sonar:ci
```

```bash
# package.json
"sonar:ci": "bash scripts/sonar-scan.sh --if-running"   # npx sonarqube-scanner, ingen devDependency
```

`sonar:ci` kör bara scanningen, utan `-Dsonar.qualitygate.wait=true` — pushen blockeras alltså inte om quality gate failar. Resultatet är informativt: studenten ser det i SonarQube-UI:t efteråt. Friktion ska komma från `npm run check` och coverage-gränsen, inte från en quality gate som ställer högre krav (80 % coverage på ny kod i hela `src/`) och som studenten inte har satt själv. Med `--if-running` kollar skriptet först `api/system/status` och hoppar över scanningen med en rad text om servern inte är uppe, så en push hänger aldrig på att SonarQube är startat.

**Varför inte pre-commit?** En pre-commit hook som blockerar på formateringsfel i kmom01 är frustrerande friktion innan studenten förstår varför. SonarQube for IDE och ESLint i editorn tar den rollen för löpande feedback. Pre-push är rätt nivå — koden är färdig nog att pushas och ska passera quality gate.

**Varför inte SonarCloud i CI:** Kursen kör privata repos i en GitHub-organisation. SonarCloud är gratis enbart för publika repos — privata kräver betalkonto. ESLint med komplexitetsregler och coverage-trösklar är en seriös CI-gate i sig.

### Pedagogisk notering

70% täckning på service-lagret är ett rimligt minimikrav. Täckning på repository-lagret fångas av integrationstesterna. Täckning på controller-lagret är sekundärt — om services är väl testade och integrationstesterna täcker happy path är risken låg.

Varning: det är lätt att fastna i mocking-djungeln. Läraren bör aktivt avråda från att mocka Mongoose, MongoDB eller hela HTTP-anrop inuti enhetstester.

### Beslutade frågor

- Bruno CLI i CI: inkluderat som valfritt issue 04-55. Contract tests i `bruno/contract/` med sekventiellt flöde. CI:s e2e-jobb kör dem automatiskt.
