Den här veckan startar du från kursens template-repo och sätter upp din devmiljö med Docker Compose. Du lär dig TypeScript-grunderna, konfigurerar Express i TypeScript och bygger de första domänspecifika REST-endpoints. Veckan avslutas med att du validerar miljövariabler med Zod — ett bibliotek du möter igen i kmom02 för att validera inkommande data.

## Kom igång

Ditt repo är förberett och finns på GitHub. Klona det till din dator:

```bash
git clone git@github.com:bth-mvc/mvc-<studentakronym>.git
cd mvc-<studentakronym>
```

Fortsätt sedan med `README.md` i repot för att installera beroenden och starta upp miljön.

### Fokus

Starta från en kurs-template och sätt upp kursens standarddevmiljö med Docker Compose. Lärdomarna handlar om TypeScript och verktygskedjan — ingenting i arkitekturen ska vara nytt den här veckan.

Studenten startar inte från noll och inte heller från sin kod i node-kursen. Kursen tillhandahåller en template med `index.ts`, `app.ts` och grundläggande projektstruktur — tillräckligt för att komma igång direkt utan att det är förifyllt.

Templaten inkluderar **färdig auth-kod** (login, logout, skyddade routes, JWT i httpOnly-cookies, bcrypt) strukturerad i lagerarkitekturen. Auth är förkunskap från node-kursen och är inte ett lärandemål i den här kursen — den finns i templaten som referensimplementation och för att kmom03:s säkerhetsmoment ska fungera från start.

Docker Compose är kursens standarddevmiljö från vecka 1 och framåt — inte ett läromoment i sig. Målet med issue 01-40 är att devmiljön är på plats och fungerar; alla efterföljande kmom förutsätter att studenten jobbar i Docker Compose. Det eliminerar "fungerar på min maskin"-problem och gör MongoDB-hanteringen trivial från och med kmom02.

### Pedagogisk notering

Introducera **inte** lagerarkitektur (controller/service/repository) den här veckan. Logiken ska samlas i routes och börja kännas plottrigt — det upplevda behovet gör att kmom02 känns motiverat snarare än som ceremoni.

SonarQube-rapporten i slutet av kmom01 förstärker det här: studenten ser *i siffror* att koden har problem. Det är ett starkare argument för refaktorering än vad läraren kan säga i en föreläsning.

SonarQube ingår förkonfigurerat i kursens docker-compose men startar inte automatiskt. Studenten kör det när de vill ha feedback: `npm run sonar`. I kmom02 kör studenten om skanningen och jämför mot baslinjen. I kmom04 formaliseras hela kedjan: SonarLint i editorn, sonar-scanner pre-push hook och ESLint + coverage i CI.

### Issue 01-35 — client-exploration

Direkt efter att `express.static()` är på plats och frontenden är synlig för första gången studeras klientkoden. Målet är inte att studenten ska förstå Svelte — utan att förstå det kontrakt deras backend behöver uppfylla.

**Vad studenten gör:**
1. Titta på `client/src/lib/state/apidoc.svelte.ts` — förstå `UNLOCK`-mappningen som kopplar SvelteKit-routes till backend-endpoints
2. Titta på `client/src/routes/portfolio/+page.svelte` — vad hämtar den och vad förväntar den sig i svaret?
3. Starta Svelte-devservern mot din körande backend: `cd client && npm run dev`
4. Navigera till `http://localhost:5173` — se vilka sektioner som är låsta och varför

### `/api/doc` som upplåsningsmekanism

Frontenden probar `GET /api/doc` vid uppstart och aktiverar UI-sektioner baserat på deklarerade endpoints. Minimalt svar vid start:

```typescript
app.get('/api/doc', (req, res) => {
  res.json({
    name: 'börsklient-api',
    version: '1.0.0',
    endpoints: [
      { method: 'GET', path: '/health' },
      { method: 'GET', path: '/api/doc' },
      { method: 'GET', path: '/api/portfolio' },
    ]
  })
})
```

Studenten utökar `/api/doc` i varje kmom när nya routes läggs till. Det är ett enkelt mönster som skapar vanan att dokumentera API:et löpande.

### Zod env-mönster

```typescript
import { z } from 'zod'

const envSchema = z.object({
  PORT: z.string().default('3000'),
  MONGODB_URI: z.string(),
  JWT_SECRET: z.string().min(32),
})

export const env = envSchema.parse(process.env)
```

Studenten har aldrig sett Zod förut. Fokus i issue 01-70 är att förstå att ett schema beskriver förväntad form, och att `parse()` kastar ett tydligt fel vid uppstart om något saknas. I kmom02 används Zod igen för att validera inkommande request-data i controllers — det är ett annat användningsfall (opålitlig användardata istället för känd konfiguration) och bygger naturligt på denna grund.
