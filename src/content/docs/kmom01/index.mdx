Den här veckan startar du från kursens template-repo och sätter upp din devmiljö med Docker Compose. Du lär dig TypeScript-grunderna, konfigurerar Express i TypeScript och bygger de första domänspecifika REST-endpoints. Veckan avslutas med att du validerar miljövariabler med Zod — ett bibliotek du möter igen i kmom02 för att validera inkommande data.

## Kom igång

Ditt repo är förberett och finns på GitHub. Klona det till din dator:

```bash
git clone git@github.com:bth-mvc/mvc-<studentakronym>.git
cd mvc-<studentakronym>
```

Fortsätt sedan med `README.md` i repot för att installera beroenden och starta upp miljön.

## Inlämning

1. Stäng alla obligatoriska issues, och de valfria som du har gjort klart.
2. Skriv klart din redovisningstext i `report/kmom01.md` och ta bort platshållartexten.
3. Verifiera att koden är ren innan du taggar:

```bash
npm run check
```

Alla kontroller ska passera — typecheck, lint, format och tester. Åtgärda eventuella fel innan du går vidare. Samma kontroller körs i CI, så här fångar du felen först.

4. Kör en självkoll som kontrollerar att redovisningstexten är klar och att alla obligatoriska issues är stängda:

```bash
npm run check-submission -- kmom01
```

5. Committa, tagga och pusha:

```bash
git add report/kmom01.md
git commit -m "Add kmom01 report"
git tag v1.0.0
git push origin main --tags
```

Kontrollera på GitHub att taggen syns under **Tags**.

Taggen startar ett CI-flöde på GitHub, under fliken **Actions**. Det kör samma kontroller som du körde lokalt, och bygger och startar dessutom appen och kör Bruno-testerna mot den. Vänta tills det är klart och kontrollera att det blir grönt. Blir det rött: öppna körningen, läs felet, åtgärda det och lämna in igen med en ny tagg (se nedan).

Behöver du uppdatera din inlämning efteråt? Committa ändringen och skapa en ny tagg med ökad patch-version, t.ex. `v1.0.1`, och pusha den. Flytta aldrig en tagg som redan är pushad.

### Fokus

Starta från en kurs-template och sätt upp kursens standarddevmiljö med Docker Compose. Lärdomarna handlar om TypeScript och verktygskedjan — ingenting i arkitekturen ska vara nytt den här veckan.

Studenten startar inte från noll och inte heller från sin kod i node-kursen. Kursen tillhandahåller en template med `index.ts`, `app.ts` och grundläggande projektstruktur — tillräckligt för att komma igång direkt utan att det är förifyllt.

Templaten inkluderar **färdig auth-kod** (login, logout, skyddade routes, JWT i httpOnly-cookies, bcrypt) strukturerad i lagerarkitekturen. Auth är förkunskap från node-kursen och är inte ett lärandemål i den här kursen — den finns i templaten som referensimplementation och för att kmom03:s säkerhetsmoment ska fungera från start.

Docker Compose är kursens standarddevmiljö från vecka 1 och framåt — inte ett läromoment i sig. MongoDB körs alltid i Docker. Efter issue 01-40 finns två lägen: dev-läge (`docker compose up -d mongodb` + `npm run dev`, med hot reload) som används för det dagliga arbetet i alla efterföljande issues, och full stack (`docker compose up -d --build`) för att kontrollera att Dockerfile och produktionsbygget fungerar. Byte från full stack till dev-läge kräver `docker compose stop api` (porten 3000).

### Pedagogisk notering

Introducera **inte** lagerarkitektur (controller/service/repository) den här veckan. Logiken ska samlas i routes och börja kännas plottrigt — det upplevda behovet gör att kmom02 känns motiverat snarare än som ceremoni.

SonarQube är ett valfritt spår (sedan 2026-10-20): en lokal SonarQube-server är för tung för många studenters datorer. Det ingår förkonfigurerat i kursens docker-compose men startar inte automatiskt — studenten kör `npm run sonar` om de vill. Den som tar en baseline i 01-15 kan jämföra efter refaktoreringen i den valfria 02-70 och lägga scannern i pre-push-hooken i den valfria 04-60. Det obligatoriska spåret är `npm run check` (och från kmom04 `npm run test:coverage`) i pre-push-hooken och ESLint + coverage i CI (kmom04). Editortilläggen (ESLint, Prettier, SonarQube for IDE m.fl.) är ett förslag, inget krav.

### Issue 01-35 — client-exploration

Direkt efter att `express.static()` är på plats och frontenden är synlig för första gången utforskar studenten appen på `http://localhost:3000`. Målet är inte att studenten ska förstå Svelte — utan att se det kontrakt deras backend behöver uppfylla.

**Vad studenten gör:**
1. Registrera ett konto och logga in
2. Se vilka sektioner som är låsta (🔒) — de låses upp när backend deklarerar motsvarande endpoints i `/api/doc`
3. Titta på hälsopanelen som läser `GET /health`
4. (För den nyfikne) Läs `client/src/lib/state/apidoc.svelte.ts`, som läser `GET /api/doc` och låser upp sektioner

"Väntar på prisdata…" och 404-fel i konsolen är väntade i det här läget.

### `/api/doc` som upplåsningsmekanism

Frontenden probar `GET /api/doc` vid uppstart och låser upp sektioner baserat på deklarerade endpoints. Studentens router efter issue 01-60:

```typescript
import { Router } from 'express'

export const docRouter = Router()

docRouter.get('/', (_req, res) => {
  res.json({
    name: 'börsklient-api',
    version: '1.0.0',
    endpoints: [
      { method: 'GET', path: '/health', description: 'Server health status' },
      { method: 'GET', path: '/api/doc', description: 'API documentation' },
      { method: 'GET', path: '/api/portfolio', description: "Current user's portfolio" },
    ],
  })
})
```

Listan innehåller bara routes som studenten själv bygger — de färdiga auth-routerna tas inte med. Dashboarden visar då 3 endpoints och 2 / 9 sektioner. Studenten utökar `/api/doc` i varje kmom när nya routes läggs till. Det är ett enkelt mönster som skapar vanan att dokumentera API:et löpande.

### Zod env-mönster

```typescript
import { z } from 'zod'

const envSchema = z.object({
  PORT: z.string().default('3000'),
  MONGO_HOST: z.string().default('localhost'),
  // ... fler variabler
  JWT_SECRET: z.string().min(32, 'must be at least 32 characters'),
})

const result = envSchema.safeParse(process.env)

if (!result.success) {
  const problems = result.error.issues.map((issue) => `  ${issue.path.join('.')}: ${issue.message}`)
  throw new Error(`Invalid environment variables:\n${problems.join('\n')}`)
}

const parsed = result.data

export const env = {
  ...parsed,
  MONGODB_URI: `mongodb://${parsed.MONGO_HOST}:${parsed.MONGO_PORT}/${parsed.MONGO_DB}`,
}
```

Studenten har aldrig sett Zod förut. Fokus i issue 01-70 är att förstå att ett schema beskriver förväntad form, och att appen stoppar vid uppstart med ett kort, tydligt fel (en rad per variabel) om något saknas. `safeParse()` används i stället för `parse()` så att felet blir en rad i stället för en lång `ZodError`. I kmom02 används Zod igen för att validera inkommande request-data i controllers — det är ett annat användningsfall (opålitlig användardata istället för känd konfiguration) och bygger naturligt på denna grund.
