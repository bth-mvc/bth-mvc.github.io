Den här veckan bygger du intelligenta tjänster ovanpå börskopplingen från kmom05. Din server gör nu mer än att relay:a data — den analyserar prisflödet, reagerar på händelser och håller sin integration robust mot fel. Det är steget från "det fungerar" till "det fungerar även när den externa servern beter sig oförutsägbart."

## Inlämning

1. (Valfritt) Kör `npm run sonar` och jämför med din förra scan. Notera förändringar i din redovisningstext.
2. Stäng alla obligatoriska issues, och de valfria som du har gjort klart.
3. Skriv klart din redovisningstext i `report/kmom06.md` och ta bort platshållartexten.
4. Verifiera att koden är ren innan du taggar:

```bash
npm run check
```

Alla kontroller ska passera — typecheck, lint, format och tester. Åtgärda eventuella fel innan du går vidare. Samma kontroller körs i CI, så här fångar du felen först.

5. Kör en självkoll som kontrollerar att redovisningstexten är klar och att alla obligatoriska issues är stängda:

```bash
npm run check-submission -- kmom06
```

Issue-kontrollen kräver att du är inloggad i GitHub CLI (`gh auth login`). Annars hoppas den över, och då behöver du själv kontrollera att dina issues är stängda.

6. Committa, tagga och pusha:

```bash
git add report/kmom06.md
git commit -m "Add kmom06 report"
git tag v6.0.0
git push origin main --tags
```

Kontrollera på GitHub att taggen syns under **Tags**.

Taggen startar ett CI-flöde på GitHub, under fliken **Actions**. Det kör samma kontroller som du körde lokalt, och bygger och startar dessutom appen och kör Bruno-testerna mot den. Vänta tills det är klart och kontrollera att det blir grönt. Blir det rött: öppna körningen, läs felet, åtgärda det och lämna in igen med en ny tagg (se nedan).

Behöver du uppdatera din inlämning efteråt? Committa ändringen och skapa en ny tagg med ökad patch-version, t.ex. `v6.0.1`, och pusha den. Flytta aldrig en tagg som redan är pushad.

7. Öppna en pull request från `main` till `bth/submit/kmom06` i ditt repo. CI körs även på pull requesten — kontrollera att den blir grön där också.

Läraren läser din redovisningstext via `report/kmom06.md` i PR:en.

### Prisnotifieringstjänsten

Studenten bygger en service som lyssnar kontinuerligt på SSE-flödet från börsen och jämför inkommande priser mot sparade trösklar i MongoDB:

```typescript
// price-alert.service.ts
class PriceAlertService {
  async checkPrice(token: string, price: number): Promise<void> {
    const alerts = await this.alertRepository.findTriggerable(token, price)
    for (const alert of alerts) {
      await this.notifyUser(alert)
      await this.alertRepository.markTriggered(alert.id)
    }
  }
}
```

När ett tröskelvärde passeras skickas notisen till frontenden via studentens egna SSE-anslutning.

### Idempotent webhook-hantering

Webhooks kan levereras mer än en gång — "at least once delivery". Utan idempotens-hantering bokas samma affär dubbelt i portfolion.

```typescript
const existing = await this.webhookLogRepository.findById(webhookId)
if (existing) return // already processed

await this.processOrder(payload)
await this.webhookLogRepository.save(webhookId)
```

### Strukturerad loggning flyttad till ops-kursen (2026-10-27)

Issuet `structured-logging` och decket "Strukturerad loggning i produktion" är borttagna ur kmom06 för att ge en lättare sista vecka. Det mesta fanns redan i 03-70 (redaction) och 03-75 (`event`-fält), och loggning blir meningsfull först när loggarna samlas i en aggregator. Se `NEXT-COURSE.md`.

### Pedagogisk notering

Idempotens är ett begrepp många studenter möter för första gången här. Det är värt att lägga tid på i föreläsning — "at least once delivery" är ett fundamentalt designbeslut i alla distribuerade system och återkommer i meddelandeköer, betalningssystem och mikrotjänstarkitekturer.

Prisnotifieringstjänsten är det roligaste momentet: studenten ser sin egen notis dyka upp i frontenden när priset passerar tröskeln.
