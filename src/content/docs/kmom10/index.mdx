Det examinerande kursmomentet. Du fördjupar och utökar börsklientappen som du byggt under kmom01–06 — inte ett nytt system, utan en meningsfull vidareutveckling av det befintliga. Projektet ska visa att du behärskar och kan motivera dina tekniska val, och att du kan ta kursens mönster ett steg längre på egen hand.

## Grundkrav — betyg E och D

Alla obligatoriska issues i kmom01–06 ska vara avslutade och börsklientappen ska fungera enligt checklistan nedan. Sedan utökas appen med två konkreta nya features.

### Verifiera att applikationen fungerar

Gå igenom listan och bekräfta att varje del fungerar:

| Funktionalitet | Kmom |
|---|---|
| `GET /health` returnerar `{ status: 'ok' }` | 01 |
| Frontenden laddas och visar korrekt data | 01 |
| Lagerarkitektur genomförd: controllers, services, repositories | 02 |
| Zod-validering på alla inkommande requests | 02 |
| Global error handler med custom error-klasser | 02 |
| Publika IDs används i URL:er (ej MongoDB `_id`) | 02 |
| CORS konfigurerat korrekt för Svelte-frontenden | 03 |
| Helmet och rate limiting aktiva | 03 |
| Inloggning, logout och skyddade routes fungerar | 03 |
| Enhetstester för services körs gröna | 04 |
| Integrationstester för controllers körs gröna | 04 |
| CI-pipeline kör lint + test + coverage | 04 |
| Pre-push hook blockerar vid SonarQube-fel | 04 |
| API-nyckel konfigurerad mot tokenbörsen | 05 |
| Köp/säljorder kan läggas och webhook tas emot | 05 |
| SSE-flöde relay:as till frontenden | 05 |
| Webhook-hantering är idempotent | 06 |
| Retry-logik mot börsen är aktiv | 06 |
| Prisnotifieringar fungerar via SSE | 06 |
| Strukturerad loggning — känslig data loggas inte | 06 |

### Utöka börsklientappen

Under kmom05 och kmom06 fanns valfria issues som du kunde göra om du ville utforska vidare. Nu blir de värdefulla — implementera minst **två** av dem som en del av grundkravet.

Har du redan gjort dem under kursens gång? Då räknas de — verifiera att de fungerar och beskriv dem i redovisningstexten.

| Issue | Namn | Vad du bygger | Synligt i klienten |
|---|---|---|---|
| 05-65 | `trade-history` | `GET /api/trades` med cursor-pagination, handelshistorik | Trades-sidan låses upp |
| 06-55 | `order-history` | Visa användarens ordrar med status (pending/matched/cancelled) | Orders-sidan utökas med lista |
| 06-60 | `portfolio-analytics` | `GET /api/me/stats` — avkastning per token, handelsvolym, bäst/sämst presterande | Ny sektion på Portfolio-sidan |

Varje utökning som exponerar en ny endpoint ska läggas till i `/api/doc` så att frontenden låser upp motsvarande vy. Studenter som redan gjort en valfri issue under kursen har den redo — läraren ser det direkt i frontenden.

Beskriv implementationen och dina designbeslut i redovisningstexten.

## Optionella krav — betyg C, B och A

Varje krav höjer betyget ett steg. Krav 1 och krav 2 är fristående. Krav 3 kräver att båda är avklarade. Beskriv vad du gjort och varför i redovisningstexten.

### Krav 1 — Testning (betyg C)

Skriv tester för de utökningar du implementerade i grundkravet:

- Enhetstester för services med mockade repositories
- Integrationstester för controllers med Supertest + `mongodb-memory-server`
- Minst 70% radtäckning på service-lagret
- Testerna körs i CI utan beroende av extern databas

Beskriv vad du testade, varför du valde just de fallen och vad du *inte* testade och varför.

### Krav 2 — Kodkvalitet och CI (betyg B)

- ESLint med regler för `max-lines-per-function` och `complexity`
- Coverage-rapport i CI med definierad gräns
- Pre-push hook med sonar-scanner — quality gate blockerar push vid nya code smells
- Beskriv vilka kvalitetsproblem verktygen hittade och hur du hanterade dem

### Krav 3 — Eget val (betyg A)

Kräver att krav 1 och krav 2 är avklarade.

Välj och implementera en backend-feature som inte ingår i grundkraven eller de optionella issuerna. Valet ska motiveras och implementationen ska dokumenteras.

**Inspiration — inte en begränsad lista:**

| Idé | Vad det innebär |
|---|---|
| Refresh tokens | Token rotation, secure storage, revocation |
| Caching | HTTP cache-headers (ETag, Cache-Control) på tunga GET-endpoints |
| Avancerad sökning | Fulltextsökning i MongoDB, relevansordning |
| Webhooks ut | Din server *skickar* webhooks till en registrerad URL när något händer |
| Avancerat CI | Branch protection, automatisk deploy, contract testing med Bruno |
| Orderhantering | Avbryt pending order, spåra orderstatus (pending/matched/cancelled) |

## Redovisning

Se till att följande frågor besvaras i din redovisningstext i `report/kmom10.md`.

1. För varje krav du implementerat (grundkrav inklusive utökningar, och krav 1–3), skriver du ett textstycke om ca 5–10 meningar där du beskriver vad du gjort och hur du tänkt. Poängsättningen tar sin start i din text så se till att skriva väl för att undvika poängavdrag. Använd rubriker så din text blir lätt att läsa.

   **Missar du att skriva/dokumentera din lösning så blir det 0 poäng. Du kan inte komplettera en inlämning för att få högre betyg.**

2. Skriv ett allmänt stycke om hur projektet gick att genomföra. Problem/lösningar/strul/enkelt/svårt/snabbt/lång tid, etc. Var projektet lätt eller svårt? Tog det lång tid? Vad var svårt och vad gick lätt? Var det ett bra och rimligt projekt för denna kursen?

3. Vilken är din TIL för detta kmom?

4. Vilken är din TIL för kursen som helhet?

5. (Valfritt) Avsluta med ett sista stycke med dina tankar om kursen och vad du anser om materialet och handledningen (ca 5–10 meningar). Återkoppla till lärarteamet och föreslå eventuella förbättringsförslag till kommande kurstillfällen.

6. (Valfritt) Är du nöjd/missnöjd? Kommer du att rekommendera kursen till dina vänner/kollegor? På en skala 1–10, vilket betyg ger du kursen?

```bash

git tag kmom10
```

### Krav 1–3 — ännu ej beslutade (2026-06-24)

Grundkraven (checklista + 2 valfria issues) är klara. Krav 1–3 behöver omarbetas. Riktning:

**Kodkvalitet som krav** — SonarCloud/SonarQube, ESLint-regler, coverage. Testning bör vara en del av kvalitetskravet, inte fristående ("skriv tester för din feature" istället för "skriv tester").

**Egen feature med alla lager** — studenten har hittills följt guidade issues utan att skriva egen kod från scratch. Kmom10 bör kräva att de implementerar en ny feature som rör alla lager (model → repository → service → controller → route). Problemet med "eget val" är att språnget kan vara för stort. Bättre med ett definierat mål.

**Robot-handel som feature** — studenten implementerar en enkel trading bot:
- Lyssnar på SSE-prisflödet
- Analyserar priser med en enkel strategi (t.ex. köp vid 5% dip, sälj vid 5% stigning)
- Lägger ordrar automatiskt via exchange API
- Kräver alla lager: model (strategi/config), service (logik), client (orders), SSE (priser)
- Naturligt motiverande: leaderboarden visar vem som handlar bäst
- Scope styrs av ambitionsnivå: enkel threshold-bot (C) vs avancerad strategi (A)

**Vad som behöver bestämmas:**
- Exakt betygskoppling krav 1–3
- Om robot-handel ersätter "eget val" eller är ett alternativ
- Hur man bedömer bot-kvalitet (kod, inte avkastning)
