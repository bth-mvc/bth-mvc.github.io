Den här veckan kopplar du din server som *klient* mot den gemensamma tokenbörsen — ett levande system där alla studenter på kursen är aktiva deltagare. Det är ett medvetet skifte: du implementerar inte längre vad läraren specificerar — du integrerar med ett system du inte kontrollerar. Tekniken är känd (REST, webhooks, SSE) men kontexten är ny och motivationen omedelbar: dina ordrar påverkar priser som alla andra studenter ser i realtid.

```bash

```

6. Committa, tagga och pusha:

```bash
git add report/kmom05.md
git commit -m "Add kmom05 report"
git tag v5.0.0
git push origin main --tags
```

Kontrollera på GitHub att taggen syns under **Tags**.

Taggen startar ett CI-flöde på GitHub, under fliken **Actions**. Det kör samma kontroller som du körde lokalt, och bygger och startar dessutom appen och kör Bruno-testerna mot den. ### Fokus

Studenten är inte längre ensam i sin sandbox. Deras ordrar påverkar priser som alla andra studenter ser i realtid. Tekniken är känd — REST, webhooks, SSE — men kontexten är ny och motivationen omedelbar.

### Tokenbörsen — konceptet

Alla studenter delar en gemensam börsserver med ett fast antal förskapade tokens:

- Vid **första autentiserade anropet** skapas en plånbok automatiskt med startbalans och initial tokenfördelning
- En **matchningsmotor** parar ihop ordrar automatiskt: lägsta säljpris möter högsta köppris
- Alla affärer är publika — **marknadsflödet** visar i realtid vad som händer

Tokentyper:

| Typ | Exempel | Beteende |
|---|---|---|
| **Stabil** | FIKA, SUDO | Låg volatilitet, säker hamn |
| **Volatil** | YOLO, DEPLOY, MEME | Stora prissvängningar, hög risk/reward |
| **Yield** | HODL | Tänkt att betala utdelning till innehavarna. Inte byggt i börsen (2026-10-26), bara typen finns |

### Börsserverns API (byggt, v1.3.0)

```
GET  /assets                      — alla tokens med typ och aktuellt pris
GET  /assets/:id/orderbook        — aktiva köp- och säljordrar för en token
POST /orders                      — lägg en order (köp/sälj), högst 10 % från referenspriset
GET  /trades                      — genomförda affärer (paginerat, cursor)
GET  /portfolio                   — studentens plånbok på börsen
GET  /leaderboard                 — portföljvärde, rankat (market makern markerad)
GET  /market/feed                 — SSE: priser och affärer
GET  /webhooks/pending, POST /webhooks/pending/ack, GET /webhooks/secret — polling av webhooks
```

Live på `https://exchange.dbwebb.se` (Swagger på `/docs`), deploy vid `v*`-tagg. Startbalans 100 000. Market makern **Marvin** (`marvin`) lägger passiva ordrar på båda sidor så att det finns likviditet, med en gräns för hur stor position han tar. Mocken har samma API och en exempel-leaderboard med Marvin.

### Förutsättning

Börsen måste vara driftsatt *innan* kursen startar. Den ska:
- Kräva API-nyckel (en per student)
- Ha rate limiting med tydliga headers (`X-RateLimit-Remaining`, `Retry-After`)
- Ha Swagger/OpenAPI-dokumentation
- Exponera paginerade endpoints med cursor
- Skicka HMAC-signerade webhooks vid ordermatchning
- Streama marknadsflödet via SSE

En lokal mock-server tillhandahålls för att studenter ska kunna testa utan att påverka den gemensamma marknaden under utveckling.

### SSE-kedjan

```
Börsservern  →  SSE-flöde  →  Studentens server  →  SSE  →  Svelte-frontend
```

Studentens server är en *relay* — den prenumererar på börsens flöde och vidarebefordrar relevanta händelser till sin frontend. Det är ett vanligt mönster för att filtrera och aggregera realtidsdata.

### Webhook-leverans — beslutad strategi (2026-06-22)

Webhooks kräver att studentens server är nåbar. Tre alternativ utvärderades:

1. **ngrok/tunnel** — fungerar men lägger till ett externt verktyg och signup
2. **Polling-endpoint** — börsen sparar payloads, studenten pollar `GET /webhooks/pending`
3. **Mock-server lokalt** — mock-servern skickar webhooks direkt till `localhost:3000`

**Beslut: kombination av 1 (mock lokalt) och 2 (polling live).** Byggt 2026-10-25.

- **Under utveckling:** mock-servern (05-10) kör lokalt och skickar webhooks till `localhost:3000`. Ingen tunnel behövs. Studenten implementerar HMAC-verifiering och webhook-hantering — fullt lärandemål.
- **Mot live-börsen:** börsen pushar inget utan köar signerade webhooks per student. Studenten pollar `GET /webhooks/pending` och kvitterar med `POST /webhooks/pending/ack` efter hanteringen (en okvitterad webhook kommer igen). Signaturen (`sha256=<hex>` av `body`) verifieras med samma kod som vid push. Hemligheten hämtas från börsen med `GET /webhooks/secret`.
- **Mocken gör båda:** den pushar och köar samma webhook, så pollern kan byggas mot mocken och idempotensen (06-20) får ett verkligt skäl: samma webhook kommer två gånger.
- **En wallet per API-nyckel:** studentens app kopplar ett lokalt konto (`EXCHANGE_USER_EMAIL`) till börsens wallet; det kontots portfölj speglar börsens.
- **Valfritt:** studenter som vill kan använda ngrok mot live-börsen, men börsen pushar inte, så det ger inget.

### Varför HMAC-signaturverifiering är obligatoriskt

Webhooks triggar portfoliouppdateringar. Att verifiera att de faktiskt kom från börsen är inte valet — det är kravet. HMAC-signaturer är mönstret GitHub, Stripe och Slack använder. Verifieringslogiken är identisk oavsett om webhooken levereras via push (mock/ngrok) eller poll (live-fallback).

### Pedagogisk notering

Det gemensamma marknadsflödet gör att studenter naturligt ser varandras arbete. "Varför rör sig FIKA-priset just nu?" skapar diskussioner som inte behöver orkestreras av läraren — ett av de sällsynta momenten där engagemanget driver sig självt.

### Valfria issues — bedömning (2026-06-23)

**05-65 (trade-history, cursor-pagination):** Tillför nytt koncept. Cursor-pagination är det verkliga mönstret för tidsseriedata och dyker upp i de flesta professionella API:er. Värt att behålla som valfri.

**socket-client (gamla 05-70):** Borttagen (2026-06-24). Socket.io är förkunskap från node-kursen och tillför inte tillräckligt. Socket.io mellan containers (sticky sessions, reverse proxy) är ett ops-ämne — noterat i NEXT-COURSE.md. Numret 05-70 används sedan 2026-10-26 av `portfolio-market-value` (obligatorisk).

**OBS:** Quizen nämner cursor-pagination men det täcks bara av den valfria 05-65. Antingen gör 05-65 obligatorisk eller ta bort cursor-frågan från quizen.

### Omfattning — notering (2026-06-23)

Kmom05 har sju obligatoriska issues och är den mest kodintensiva veckan. Studenten bygger: exchange client mot mocken, market service, orderläggning, webhook-mottagning med HMAC, portföljuppdatering från webhooks, SSE-relay och portföljvärdering efter marknadspris.
