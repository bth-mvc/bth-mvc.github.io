Den här veckan refaktorerar du koden från kmom01. Logiken som samlades i routes bryts upp i tre separata lager — controllers, services och repositories — och du lägger till en ny felklass i felhanteringen och Zod-validering av inkommande data. Valfritt kan du flytta genereringen av publika IDs till repository-lagret och mäta refaktoreringen i SonarQube.

Det här är arkitekturen du bygger. En HTTP-request rör sig nedåt genom lagren — varje lager har ett enda ansvar och vet ingenting om lagren ovanför.

```
HTTP Request
    ↓
Router          (definierar URL-mönster och middleware)
    ↓
Controller      (läser req, skriver res)
    ↓
Service         (affärslogik — inga Express-typer)
    ↓
Repository      (all databaskod — inga Express-typer)
    ↓
MongoDB
    ↓
HTTP Response
```

Issues 02-10 till 02-30 bygger de tre mittlagerna ett i taget. Issues 02-40 och 02-50 förfinar arkitekturen med felhantering och validering.

## Inlämning

1. Stäng alla obligatoriska issues, och de valfria som du har gjort klart.
2. Skriv klart din redovisningstext i `report/kmom02.md` och ta bort platshållartexten.
3. Verifiera att koden är ren innan du taggar:

```bash
npm run check
```

Alla kontroller ska passera — typecheck, lint, format och tester. Åtgärda eventuella fel innan du går vidare. Samma kontroller körs i CI, så här fångar du felen först.

4. Kör en självkoll som kontrollerar att redovisningstexten är klar och att alla obligatoriska issues är stängda:

```bash
npm run check-submission -- kmom02
```

5. Committa, tagga och pusha:

```bash
git add report/kmom02.md
git commit -m "Add kmom02 report"
git tag v2.0.0
git push origin main --tags
```

Kontrollera på GitHub att taggen syns under **Tags**.

Taggen startar ett CI-flöde på GitHub, under fliken **Actions**. Det kör samma kontroller som du körde lokalt, och bygger och startar dessutom appen och kör Bruno-testerna mot den. Vänta tills det är klart och kontrollera att det blir grönt. Blir det rött: öppna körningen, läs felet, åtgärda det och lämna in igen med en ny tagg (se nedan).

Behöver du uppdatera din inlämning efteråt? Committa ändringen och skapa en ny tagg med ökad patch-version, t.ex. `v2.0.1`, och pusha den. Flytta aldrig en tagg som redan är pushad.

### Fokus

Kursens kärna. Refaktorera från logik-i-routes till ett rent lagersystem. Det pedagogiska momentet är att studenten *redan har sett problemet* (routes som svämmar över från kmom01) innan lösningen presenteras.

Arkitekturen som introduceras:

```
HTTP request
   ↓
Router (route-definition only)
   ↓
Controller (req/res, validering med Zod)
   ↓
Service (affärslogik, vet ingenting om req/res)
   ↓
Repository (all databas-kod, vet ingenting om Express)
   ↓
Response (DTO)
```

### Vad frontenden låser upp

Nästan ingenting — och det är poängen. Portfolioöversikten och auth-formulären som fungerade i kmom01 ska fortsätta fungera efter refaktoreringen. Frontenden är det implicita regressionstestet: om den slutar fungera bröt studenten något i refaktoreringen.

Undantag: när 02-50 deklarerar `GET /api/portfolio/holdings/:token` i `/api/doc` blir varje innehav i portföljen klickbart och öppnar en detaljvy (`/portfolio/:token`). Dashboardens "Innehav" visar 0 kr även med innehav, eftersom klienten väntar sig fältet `holdingsValue` som bara finns i lösningen.

### Pedagogisk notering

Auth-koden i templaten är kursens referensimplementation av lagerarkitekturen. Innan studenten börjar refaktorera sin egen kod bör läraren gå igenom auth-koden i föreläsning och visa hur `auth.controller.ts`, `auth.service.ts` och `user.repository.ts` hänger ihop. Studenten har då ett konkret, fungerande exempel att jämföra med — inte bara ett abstrakt diagram.

Refaktoreringen i kmom02 är därmed inte en övning i att uppfinna mönstret, utan i att applicera ett mönster studenten redan sett i praktiken.

Läraren bör i föreläsningen visa refaktoreringen som en levande process: börja med en route full av logik och bryt upp den steg för steg live. Det är svårt att förmedla *varför* i text.

### SonarQube — andra mätpunkten (valfri)

När refaktoreringen är klar kan studenten (valfria 02-70) köra `npm run sonar` igen och jämföra med baslinjemätningen från 01-15. Förvänta dig inte ett tydligt bevis i siffror. Testkörning i mvc-claude5 (2026-10-23): maintainability issues 9 → 3 (men nästan alla borttagna var TODO-kommentarer som kmom01 löste, inte lagren), cyklomatisk komplexitet 57 → 64, funktioner 31 → 41, komplexitet per funktion 1,84 → 1,56, rating A båda gångerna, duplicering 0 % båda gångerna, coverage 31,6 → 15,9 %. Baslinjen tas tidigt i kmom01 och kmom01:s portfolio-route är en stub, så det finns lite route-logik att flytta. Issuen gör därför en poäng av vad verktyget inte ser: att controllern inte längre pratar med databasen och att servicen kan anropas utan Express.

Eftersom SonarQube-spåret är valfritt får föreläsningen bära argumentet för lagerarkitektur: visa före/efter i koden (kortare funktioner, ett ansvar per lager, testbarhet).

### Publikt ID med nanoid

Routes i node-kursen använde MongoDB `_id` direkt i URL:er. Det läcker implementationsdetaljer och gör IDs instabila vid schema-migrationer. `publicId` finns redan på `User` i templaten och genereras i `auth.service.ts`; valfria 02-60 flyttar genereringen till repository-lagret, där den hör hemma:

```typescript
import { nanoid } from 'nanoid'

// I repository, vid create:
const publicId = nanoid()   // → "V1StGXR8_Z5jdHi6B-myT"
```

Mongoose-dokumentet får ett extra fält `publicId`. Routes och controllers exponerar bara `publicId` — aldrig `_id`.

### DTOs

Beslut: Zod-inferens räcker (`z.infer<typeof schema>`), inga egna DTO-klasser. 02-50 exporterar `HoldingParams` från controllern men skickar bara vidare token-strängen; varje lager har egna interfaces (`Holding` i service och repository) så att en formändring i ett lager inte bryter de andra.
